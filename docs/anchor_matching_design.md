# アンカーマッチング改善設計

## 基本思想

**安全性が担保できないなら破棄。** 誤ったアンカーが1つでもあると、
そこから連鎖的に誤配置が発生する。マッチ数より正確性を最優先する。
周回を重ねれば自然にアンカーは増えるため、無理に選出する必要はない。

---

## 段階的アンカー決定アプローチ

各 Phase で確定したアンカーを次の Phase の基準点として活用する。
前の Phase の結果を使うことで、後の Phase の精度が向上する。

### Phase 1: tap + テキストあり（最も確実）

- **対象**: tap エッジで繋がるノードのうち、テキストがあるもの
- **マッチ条件**:
  - テキスト完全一致（または前方一致）
  - phash 類似度が閾値以上（二重確認）
  - 時系列順序の整合性
- **複数候補がある場合**: マッチしない（曖昧なら保留）

### Phase 2: auto + テキストあり

- **対象**: auto エッジで繋がるノードのうち、テキストがあるもの
- **マッチ条件**:
  - テキスト完全一致（または前方一致）
  - phash 類似度が閾値以上
  - Phase 1 アンカーとの相対位置で検証
- **例**: Phase 1 で A と C が確定済み → S2 の A'-C' 間にある auto テキストノード B' は、
  S1 の A-C 間のノードに候補を限定できる

### Phase 3: tap + テキスト空

- **対象**: tap エッジで繋がるノードのうち、テキストがないもの
- **マッチ条件**:
  - phash 類似度が高閾値以上（テキストがないため phash 頼み）
  - Phase 1+2 アンカーとの相対位置で候補を限定
  - 前後のアンカーが確定していなければマッチしない
- **リスクが高い**: 候補が1つに絞れない場合は必ず保留

### 対象外: auto + テキスト空

- 動画フレーム、暗転、ダウンロード画面など
- キャプチャタイミング依存で不安定
- **マッチ対象外**

---

## 時系列整合性チェック

### 原理

S1 のマスターノードの sort_order は確定済み。
S2 のノードの discovered_at（時系列）順序と、マッチ先の sort_order 順序が
一致していなければ、誤マッチの可能性が高い。

### 検証方法

```
S1 アンカー確定済み: A(sort=0), C(sort=5), E(sort=10)
S2 の候補 X: S2 時系列で A' と C' の間にある
→ X のマッチ先は sort 0〜5 の間のノードに限定
→ 候補が1つなら確定、複数ならスコアで選択 or 保留
```

### 矛盾検出

S1 で A(sort=3) → B(sort=7) の順だが、S2 で B' → A' の順に出現:
→ **両方のアンカーを破棄**（誤マッチの可能性が高い）

---

## 安全装置（厳格）

1. **曖昧なら保留**: 候補が複数で絞れなければマッチしない
2. **矛盾検出 → 破棄**: 時系列順序が矛盾したら関連するアンカーを無効化
3. **Phase 間の整合性検証**: 各 Phase 終了後に全アンカーの時系列整合性を確認。
   矛盾があれば後から追加したアンカーを破棄
4. **テキスト + phash の二重確認**: テキスト一致だけでは不十分、phash も確認
5. **安全性が担保できないなら破棄**: 判断に迷ったらマッチしない

---

## ノード種別ごとのアンカー信頼度

| ノード種別 | テキスト | アンカー信頼度 | 備考 |
|-----------|---------|--------------|------|
| tap + テキストあり | 安定 | 最高 | Phase 1 で最初に決定 |
| auto + テキストあり | 安定 | 高 | テキスト一致なら tap と同等 |
| tap + テキスト空 | phash 依存 | 中 | 前後アンカー必須 |
| auto + テキスト空 | 不安定 | - | マッチ対象外 |

---

## 既知のリスクと対策

### リスク1: 誤アンカーの連鎖

Phase 1 で誤マッチしたアンカーが Phase 2, 3 の基準点になると後続が全て狂う。

**対策**: Phase 1 のマッチ条件を最も厳しく設定（テキスト完全一致 + phash + 候補一意）

### リスク2: テキスト前方一致によるクラスタ統合

クラスタリングで前方一致テキストが同一ノードに統合されている場合、
マスター側のテキストがセッション側と異なる可能性がある。

**対策**: マッチ時は代表テキストの完全一致 + 前方一致で検索

### リスク3: チュートリアル内でのテキスト重複

同じセリフがチュートリアルの異なる場面で出現する可能性。

**対策**: 時系列整合性チェックで正しい方にマッチ。
両方が時系列的に有効なら保留（曖昧なので破棄）

---

## 実装方針

- `_compute_matches` を Phase 1 → 2 → 3 の段階的実行に書き換え
- 各 Phase は独立したメソッド
- Phase 間で整合性チェックを実行
- SafeInsertStrategy と組み合わせて、挿入も安全性を保証
