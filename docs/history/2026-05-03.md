## 重要な設計判断 (議論経過のうち重要なもの)

### 1. 既存 `lc_master_nodes.scene` カラムには触らない

検出器の推定 (auto_pilot の操縦制御用) と、ユーザー管理の分類タグは別物。Gemini プロンプトのヒントとして渡すのみ。

### 2. Gemini 判定対象は代表ノードのみ

クラスタ単位ではなくマスターノード単位。コスト効率と整合性のため。代表が変わったら旧タグは破棄して再判定。

### 3. キャッシュキーに description を含める

`prompt_hash` 計算範囲: プロンプト本文 + 候補タグの (id, name, description)。
- description 編集 → ハッシュ変化 → 自動再判定
- color / sort_order 変更 → ハッシュ不変 → キャッシュ維持

ユーザーから「料金次第で変える可能性あり」 (= description 編集毎にフル再判定はコスト的に許容できないかも、という保留事項)。

### 4. 操縦カテゴリは UI から名称変更不可

「カテゴリ名とタグ名が合わないリスクがある」というユーザー懸念から、コード定義のみ。
- `OperationTag` IntEnum に ID 定義 → 起動時 DB upsert
- ID は再利用禁止 (reserved)
- 廃止する場合は `_DEPRECATED` コメントで残す

### 5. シーンタグは 1 個必須 (アプリ側ガード)

Gemini に「必ず 1 つ選ばせる」プロンプト精度がこの機能の核心。手動付与時は既存シーンタグを置換 (物理削除 + 履歴記録)。

### 6. 操縦カテゴリは UNIQUE 制約のみで重複防止

screen_recorder は新規 master_fp 作成時 / 既存 master_fp 訪問時の両方で `INSERT OR IGNORE` を実行。新規 cluster が後から作られるケースに対応。

### 7. プロンプト編集 + テスト判定 5 件サンプル

Phase 3 で実装。プロンプト変更時のキャッシュ無効化警告も UI で表示。

### 8. Cost タブとの完全統合

新規コスト計算は実装せず、既存の `record_api_usage` + `COST_PRICING` + リアルタイム JPY 為替を活用。バックエンドは推定トークン数のみ返す → フロントで `calcCost()` / `fmtCost()` で表示。

### 9. API ファイル分割

機能別の 3 ファイル分割。既存 `search.php` は機能していないので Phase 4 完了後にクリーンアップ予定。

## 棄却された案 (議論経過から)

| 棄却案 | 理由 |
|---|---|
| タグ定義を version 横断で完全共通 (案 C) | 同じ master_fp が複数 version にある場合のヒント利用は OK だが、付与は version 単位の方が運用柔軟 |
| 詳細タグをシーン依存にする (「バトルダイアログ」「ホームダイアログ」など) | タグ命名爆発、検索時のシーン横断利用に不便 |
| 前後ノード情報を最初から Gemini に送る | 前後ノードのタグが未付与の段階では情報源にならない、MVP では検出器 scene のみ |
| マイグレーション用の独立ファイル | 既存パターン (`_init_db()`) との一貫性が高い |
| 全件再タグ付け時に手動タグも自動上書き | 「完全リセット」チェックボックスで明示的に選択させる方が安全 |
| プロンプト編集 UI を最初から両タグ用に統合 | Phase 3 でシーンのみに絞り、Phase 4 で詳細にも拡張する積み上げ式 |
