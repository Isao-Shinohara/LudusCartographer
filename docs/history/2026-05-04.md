## 主要実装

### 1. DB Migration (`crawler/tools/batch_processor.py`)

`_migrate()` 末尾に `_migrate_tags()` 呼び出しを追加。新規 5 テーブル + 7 index + シーン 11 / 詳細 9 の初期データ。

#### テーブル一覧
- `lc_tags` — タグ定義 (operation/scene/sub_scene)
- `lc_master_node_tags` — タグ付与 (master_fp × version_id × tag_id 多対多)
- `lc_tag_judgments` — Gemini 判定キャッシュ (P3 で利用)
- `lc_master_node_tag_history` — 代表変更履歴 + 手動編集履歴
- `lc_tag_prompts` — プロンプトテンプレート (P3 で利用)

#### 重要な実装詳細
- **重複防止**: `(name, tag_type)` の DB UNIQUE 制約はないため、初期データ INSERT は `INSERT ... WHERE NOT EXISTS` 形式で。`INSERT OR IGNORE` は使えない (PK 衝突しか防げないため)
- **code_key 部分 UNIQUE**: `CREATE UNIQUE INDEX ... WHERE code_key IS NOT NULL AND is_deleted = 0` で論理削除タグの再利用を許可
- **冪等性**: 2 回 migration を回しても初期データ件数が変わらないことをテストで担保

### 2. 代表変更ハンドラ (`crawler/tools/cross_session_merger.py`)

`_record_rep_change_history` と `_cleanup_gemini_tags_on_rep_change` を新規メソッドとして追加し、既存 orphan 修復ループ (line 673-687) にフックを挿入。

#### フック対象 (`cross_session_merger.py:673-687`)
unmerge 時の orphan 修復で `lc_master_nodes.representative_screen_id` が UPDATE される箇所が **唯一の rep 変更ポイント** (Phase 1 段階)。新規 INSERT パス (line 432 / 748 / 866) は対象外 (= 「変更」ではないため)。

#### 挙動
1. 現在付与されている全タグ ID を `lc_master_node_tag_history` に snapshot (version ごとに 1 行)
2. `assigned_by='gemini'` のタグだけ物理削除
3. `assigned_by='auto_pilot'` / `'manual'` は保持 (= ユーザー判断と操縦履歴は代表に依存しない)

Phase 1 段階では Gemini タグが存在しないので production では DELETE 0 件で動作。pytest で挙動を担保。

### 3. tags.php API (`web/public/api/tags.php` + `_tag_helpers.php`)

#### エンドポイント (7 つ)
- `GET ?type=...&include_deleted=...` → タグ一覧 (assigned_count 込み)
- `POST` → タグ新規作成 (operation は 400 拒否)
- `PUT ?id=...` → タグ更新 (is_system=1 は 403 拒否)
- `DELETE ?id=...` → 論理削除 + 影響件数返却 (is_system=1 は 403 拒否)
- `GET ?master_fp=...&version_id=...` → ノードタグ一覧
- `POST ?master_fp=...&version_id=...` → 手動付与 (シーンは置換 + manual_scene_replaced 履歴)
- `DELETE ?master_fp=...&version_id=...&tag_id=...` → 手動解除 (manual_unassigned 履歴)

#### 共通ヘルパ (`_tag_helpers.php`)
SQLite 接続、JSON レスポンス、リクエストボディ解析、色/種別バリデーション、(name, tag_type) 重複チェック、HTTP メソッド override 解析。
