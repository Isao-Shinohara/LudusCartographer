### 1. process_session_bg 系の堅牢化 (3 コミット)

#### `de7f282` 二重起動・無限リトライ・PHP exec ハング解消

ユーザー報告「process_session_bg を実行すると 30 秒タイムアウト + 同じ Gemini エラーが延々と出続ける」の根本対策。

- ❶ **二重起動防止**: `auto_pilot_state` テーブルでロック (PID + age + posix_kill aliveness check)、二度押しは `already_running` で拒否
- ❷ **JSON parse 失敗時の即時リトライ**: `gemini_correct_single` で truncated レスポンスに最大 2 回リトライ (合計 3 試行)
- ❹ **N 回連続無進展で sentinel**: 3 iteration 連続で `g` が減らなければ残 NULL に空文字 sentinel を入れて打ち切り (永遠ループ防止)
- ❺ **PHP exec → popen/pclose**: `&` バックグラウンドでも shell stdout EOF を待つ仕様で 30 秒ハングしていた問題を解消

E2E 検証: 起動 0.062s で即 return (旧 30s)、iterations=4 で正常終了、ロック解放確認。

#### `20cf431` sentinel 短縮 + 進捗キー不一致バグ修正

- `NO_PROGRESS_LIMIT: 3 → 2` (待機時間 ~33% 短縮)
- phase 細分化: `OCR / synthesizing_edges / building_graph / graph`
- **既存バグ修正**: `_update_progress` が `merge_progress` キーに書いていたが PHP 側は `merge_phase` キーを読んでいたため進捗が一切表示されない不整合を統一
- ダッシュボード JS: 単一ポーリングに統合、180s で「Gemini API 遅延の可能性」警告

#### `e12febe` 削除済みセッションを Live タブから除外

進行中セッション削除後に Live タブが削除済みを「最新」として表示し続ける問題。`getSessions` の WHERE に `status NOT IN ('archived', 'discarded')` を追加。

### 2. paused 状態の導入 (1 コミット)

#### `5bdb478` paused ライフサイクル + 確定フロー

「手動停止 (Ctrl+C) で `completed` になり、知らないうちにマージタブに並んで誤マージするリスク」をユーザーが指摘。

```
running ─SIGTERM/Ctrl+C─→ paused (manual_stop)
running ─goal_reached───→ completed (goal_reached)
running ─crash──────────→ completed (orphaned)
paused ─「完了として確定」→ completed (manual_stop)
paused ─auto_pilot 起動──→ running
```

- `screen_recorder.close(goal_reached=False)` → `status='paused'` (was 'completed')
- `getRunningSessions` が running + paused 両方を返す
- 進行中タブの paused 行に「完了として確定」ボタンを表示
- 確定時は `pgrep -f auto_pilot.py` で生存チェック → 動いていたら拒否
- 既存スキーマバグ修正 (`is_representative` カラムが CREATE TABLE に欠落) も副次対応 → 23 件のテスト失敗を解消

### 3. マージプレビューの修正・機能追加 (5 コミット)

#### `518071a` seed プレビューで新規追加 0 件誤表示

マスター空 (= seed) のとき `preview_merge` が「新規追加ノード 0 件」と誤表示する不整合 (実 merge では `_seed_master` が全代表を INSERT するのに、プレビューは SafeInsert を呼んで「アンカーがないので挿入不可」と判定していた)。

修正: `is_seed=True` の場合 SafeInsert を呼ばず全 new_fps を `insertable=True` で返す。

実機検証: ap_20260428_122410 (1070 reps) で `insertable: 0/1070 → 1070/1070` ✓

#### `42b93ea` Live で不採用にした画像が merge に混入

`_compute_matches` の `session_reps` SELECT が `is_artifact` フィルタを欠いていた整合性違反 (実 merge_to_master と AnchorMatcher は除外しているのに preview だけ未除外)。

`AND COALESCE(is_artifact, 0) = 0` を追加。

#### `59d95c1` マスター OCR 手動編集時のキャッシュ自動削除

P4-P6 Gemini 判定キャッシュ (`lc_anchor_judgments`) は `(session_fp, master_fp, model)` キーだが、`master_fp` は画面 fingerprint なので OCR 手動編集しても変わらず、編集前テキストで下した古い判定が永続的に効いてしまう問題。

`update_manual_text` / `apply_correction_rule` の UPDATE 直後に該当 `master_fp` のキャッシュを `DELETE`。確認は出さず自動。

副次修正: `update_manual_text` の SELECT が `lc_master_nodes` 直接で `ocr_text_gemini` を参照していた既存バグ (`lc_screens` 側のカラム) → JOIN で取得するよう修正。

#### `62b4753` マージプレビューで新規追加ノードに「不採用」操作

ユーザー要望「Mergeのプレビューで新規追加ノードに対しても不採用選択ができるようにしてほしい」。

`is_artifact=2` (Live と同じ) を流用することで、既存の「`session_reps` から `is_artifact > 0` を除外」ロジック (`42b93ea` で追加) が自動的に効く設計。

- backend: `new_nodes` に `screen_id` 追加
- frontend: モーダルに「✕ 不採用にする (この新規ノードを除外)」ボタン
- クリック → `toggle_screen_artifact` API → プレビュー再取得

E2E: ap_20260428_122410 で screen 128507 を不採用 → new_nodes 375→374、対象消失 ✓

#### `5f8c864` shift+クリック選択 → 一括不採用に新規ノード対応

shift+クリックの対象を「アンカーのみ」→「アンカー + 新規ノード」に拡張。確定ボタンは選択を anchors / newNodes に分岐:

| 種別 | 状態保持 | UI | 取り消し |
|---|---|---|---|
| アンカー (master_fp あり) | excludedGeminiFps Set | 半透明オーバーレイ | shift+選択 + 採用 |
| 新規ノード (screen_id あり) | DB.is_artifact=2 | プレビューから消失 | Live タブから |

#### `7aa52a2` マージ実行で空ページ問題

ユーザー報告「マージ実行後にマージ待ちが 0 件、更新したら 5 件出てくる」(2 ページ目を見ていたのに件数が 1 ページに収まる量に減った場合に発生)。

## ユーザーとの主要対話

### Q. 「P4-P6 は元々自動操縦時に実行していなかった？いつからマージ時になった？」

A. 元から CrossSessionMerger 経由 (= マージ時) のみ。`9dbe3ab` (4/18) で AnchorMatcher 実装、`2c1f4ae` (4/19) で Gemini 導入、`4df7c8c` (4/20) で 6 段階に拡張。auto_pilot から呼ばれたことは一度もない。混同しやすいのは BG worker の Gemini OCR 補正 (画面 1 枚に対して整形を依頼) で、これは P4-P6 (画面ペアの同一性判定) と別物。

### Q. 「マスターが変わるとキャッシュは使われない？」

A. キャッシュキーは `(session_fp, master_fp, model)`。新ノード追加 → 自動的に新ペアでキャッシュミス → API 再リクエスト。一方、master OCR を手動編集しても `master_fp` は不変なのでキャッシュヒットしてしまう不整合があった (= `59d95c1` で修正)。

### Q. 「マージ時に Gemini プロセスが動くのなぜ？バックグラウンド未完了時にやるべきでは？」

A. P4-P6 はマスター現状との比較なのでマスター状態確定後 (= マージ時) 以外では動けない。BG 未完了の Gemini は OCR 補正 (per-screen) で別物。prefetch 設計は将来検討。
