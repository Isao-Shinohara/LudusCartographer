### コミット 2: `bcfa016` STARTUP/LOADING の誤 artifact + クラスタ統合バグ

**症状**: session 2/3 で ANIPLEX/POKELABO/注意事項のロゴ画面が「Gemini不採用」表示 + 4 つの異なる画面が同一クラスタ (1556) に統合。

**因果連鎖**:
1. `ee728cd` (4/23) で「黒ピクセル ≥50% → artifact」検出が導入
2. ANIPLEX ロゴ等は構造的に黒背景 (90%+ 黒) → 全 session で artifact 化されるはず
3. ただし session 1 のスクショだけ scrcpy/Quartz の color range 不一致で背景が pixel 値 16 (limited range) になっていて、黒比率 0.2% に → 50% 閾値を割って通過

5. 加えて検出時に `ocr_text_gemini = ''` で OCR 状態を破壊 → COALESCE で元 `ocr_text` にフォールバックできず → `_remerge_text_clusters` が「全部テキスト空」と誤認 → dHash 全 0 で類似 → 別画面が同一クラスタに統合

**修正**:
1. `_is_truncated_capture` ヘルパーを抽出 (static method)
   - scene が `STARTUP` / `LOADING` の場合は黒比率検出をスキップ
2. 検出時の DB 書き込みから `ocr_text_gemini = ''` を削除 (`is_artifact=1` のみマーク)
3. ダッシュボードの dot tooltip 「Gemini不採用」→「判定不採用 (Gemini or 黒比率)」

**既存データ修復**:
- 22 件の STARTUP/LOADING で `is_artifact=0` + `ocr_text_gemini=NULL` に戻す (Gemini が実判定した 3 件は残置)

**テスト**: `tests/test_truncated_capture.py` 11 件 pass。

### コミット 3: `707ab21` Gemini MAX_TOKENS 早期検出 + truncated sentinel

**症状**: 「内側 JSON パース失敗 (Unterminated string)」が頻発、毎バッチで同じ画面に 3 回ずつリトライ → API コスト浪費。

**原因**:
- `maxOutputTokens = 8192` を超えると Gemini が出力途中で切る (truncated)
- 規約画面・ヘルプ画面等の長文では発生
- 既存実装は内部リトライ 2 回 → 全部 truncated でも同条件で再試行 → 無駄
- `None` を返すと後続バッチで再試行 → 永続的に毎バッチ失敗

**修正 3 点**:
1. `maxOutputTokens` 8192 → **16384** に拡大 (一次対策)
2. `finishReason = "MAX_TOKENS"` の早期検出: レスポンス受信時にチェックし、即諦め (= 1 API call で終了)
3. 永続失敗時に `{"error": "truncated", "id": item_id}` marker 返却 → BG_WORKER で `ocr_text_gemini=''` (sentinel) 化 → 将来バッチで対象外

**コスト削減効果**:
| ケース | Before | After |
|---|---|---|
| 通常画面 | 1 API call | 1 API call |
| 長文画面 (8192 ぎりぎり) | 3 API calls × 毎バッチ | 1 API call (16384 で成功) |
| 16384 超過 | 3 × 毎バッチ ∞ | 1 API call、その後永遠に対象外 |

**テスト**: `tests/test_gemini_ocr.py` の更新 1 件 + 新規 2 件 (合計 18 件 pass)。

### コミット 4: `aca7bf1` タップ無効 stuck 検知

**症状**: ユーザーが朝に観察、4 分間で 86 件のキオク編成画面が記録されるアプリ側 stuck 状態。**金枠ハイライトのある画面で auto_pilot がタップを繰り返すが進まない** → 各画面が個別に Gemini に送られて API 浪費。

**実データ調査**:
- 5 分間で 86 スクリーン (~17 sec 間隔)
- 隣接 phash 距離: min=0, max=9, **平均 3.2** (微小揺れ)
- 全 86 画面間最大距離: 14
- OCR テキストはほぼ同じ (「U キオク編成 入手順 NEW...」) だが「1i」「NEW1」等の微小揺れで前方一致せず別クラスタ化
- 既存の DB `fingerprint` カラムは `ph_<phash>_<ts>` 形式でタイムスタンプ違いで毎回別 fp

**設計**: `StuckTapDetector` クラス
- 各タップ実行後、画面状態を評価
- 同一画面なら失敗 target `(action, x//30, y//30)` を set に追加
- 画面変化があれば set クリア (= 進捗あり)
- set サイズ ≥ K (=8) → STUCK 確定 → auto_pilot 停止

**同一画面判定** (`_is_same_effective_screen`):
- ① phash ≥ 15: 別画面確定
- ② OCR 両方あり (≥5字) で類似度 < 0.85: 別画面 (ADV セリフ進行を区別)
- ③ phash 範囲内 (< 15) + dHash 距離 < 20: 同一画面 (エフェクト揺れ吸収)
- ④ dHash なしフォールバック: phash < 5

**OCR は「区別する方向にのみ」使う非対称設計**:
- phash 似てても OCR 大きく違う → 別画面 (セリフ進行検知)
- phash 違うのに OCR 似てる → merge はしない

**統合**:
- `tap_device` で `last_tap_action/x/y` を CycleState に記録
- メインループ OCR 後に `stuck_detector.evaluate` 呼び出し
- STUCK 確定で `recorder.close + bg_worker.stop + break` (status='paused')

**誤検知防止 (テストで検証)**:
- ADV セリフ進行 (10 セリフ): OCR 類似度低でリセット → 検知しない
- バトル進行 (HP/ダメージ変化): OCR 類似度低でリセット → 検知しない
- ロード待ち: タップしないので set 増えない → 検知しない
- TUTORIAL_TAP の 6 段階フォールバック (+0/30/60/90/120/150px): 30px 単位丸めで集約 → 6 distinct のみ
- 30px 以内の同位置再タップ: 二重カウントしない

**テスト**: `tests/test_stuck_detector.py` 19 件 pass。

## ユーザーとの主要対話

### 「session 1 のロゴだけ採用された理由」深掘り
当初「scrcpy のキャプチャノイズ」と説明 → ユーザー指摘で詳細調査:
- 実画像比較で session 1 ANIPLEX 背景は dark gray (~16)、session 2/3 は pure black (0)
- 中央 80% 領域の暗 pixel 最頻値: session 1=**16-17 一定**、session 2/3=**1 一定**
- → H.264 limited range vs full range の違い (BT.601/BT.709 仕様)

### 「scrcpy 起動時テスト」で再現試行
- 端末 USB 接続、scrcpy 各種 encoder 試行 (h264 hw/sw, h265, warmup time)
- すべて full range (pixel 値 0) で再現できず
- 結論: 「session 1 だけ違った理由」は当時の scrcpy/Mac 環境に依存し未解明、修正方向には影響しない

### Gemini コスト対策の議論経過
ユーザーから「API コストが無駄にかかっているのが気になる、その場合も sentinel」 → MAX_TOKENS 早期検出を追加し 3 API call → 1 に削減。

### Stuck 検知の議論経過
- 案 1A (時間ベース) vs 案 1B (タップベース) → ユーザー: 1B のみで実装
- 候補アクション複数の扱い → ユーザー: 1 カウント、K 上限
- fingerprint 一致判定 → エフェクト揺れに強い phash + dHash + (OCR 類似度) の非対称判定
- ADV セリフ進行誤検知の懸念 → OCR 類似度を「区別する方向のみ」使う設計
