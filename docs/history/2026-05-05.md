### グループ 3: production バグ修正 (DB lock + LB 誤検出)

#### 3a: `lc_ocr_noise_words` テーブル migration

| コミット | 内容 |
|---|---|
| `2bd3cc6` | batch_processor._migrate に CREATE TABLE 追加 (周回完了時のみ走る) |
| `5442514` | screen_recorder._migrate にも追加 (起動時必ず走る、本命) |

症状: fresh install + Gemini 補正バッチで `no such table: lc_ocr_noise_words` 警告。entire batch がロールバックされ Gemini OCR 補正の結果が消失。

原因: テーブルは `web/public/api/handlers/ocr.php` の `add_noise_word` API でだけ lazy CREATE される設計。fresh install では誰も先に作っていない。

修正: ScreenRecorder 起動時に確実に CREATE。batch_processor 側にも同コードを残置 (IF NOT EXISTS で重複無害)。

検証: 修正後 `no such table` 警告 0 件。ノイズ語辞書が 5 → 18 → 41 → 56 → 71 → **77** と継続蓄積。

#### 3b: `detect_login_bonus_popup` 誤検出と過剰棄却の連鎖

LOGIN_BONUS 検出器が ADV シーンで誤発火する問題と、修正が過剰になり本物の LB を棄却する問題を順次対処。

| コミット | 内容 |
|---|---|
| `cae9511` | 案 A: 矩形 inset 要件 (画面端 ≥40px) 追加 |
| `10587d3` | inset 閾値を 40 → 20 に緩和 (本物 LB が棄却される副作用解消) |

##### Step 1: ADV シーンでの誤発火 (02:38 観察、cae9511 で対処)

症状: ADV (キャラ会話) シーン中に LOGIN_BONUS_CLOSE が誤発火し、icon_skip 座標 (1370, 56) をタップ → ストーリースキップ確認ダイアログ表示。`STORY_SKIP_CANCEL` で復旧したが誤動作。

原因: `detect_login_bonus_popup` の判定が緩く、ADV シーン遷移フレームで全画面を矩形と Sobel 検出し、icon_skip も合わせて検出 → 全条件通過。

修正 (cae9511): 矩形が画面端から 40px 以内 inset の場合は棄却。ADV 遷移フレーム (rect 端 0-15px) を完全棄却。

##### Step 2: 本物 LB 画面が棄却される副作用 (03:41 観察、10587d3 で対処)

症状: チュートリアル後の本物のログインボーナス画面で `detect_login_bonus_popup` が反応せず、フォールバックの WFC_ESCAPE が偽の close_btn (Day 1 タブ付近) を 5 分以上タップ続けるループ。

原因: 本物の LB 画面は `inset=L206 T34 R168 B60` で、Top=34px が 40px 閾値で棄却されていた。

検証 (実機キャプチャ画像で再現テスト):
```
[修正前] [LOGIN_BONUS] 矩形が画面端 → 棄却 inset=L206 T34 R168 B60 (<40)
[修正後] [LOGIN_BONUS] 検出: rect=(206,34)-(1272,660) 面積比=64.4% icon_skip=(1383,33 score=0.95)
```

修正 (10587d3): 閾値 40 → 20。ADV 誤検出 (Top=15/Bottom=2) は引き続き棄却、本物 LB (Top=34) は通過。

### グループ 4: WriteWorker — DB lock 競合の完全排除 (1 commit)

| コミット | 内容 |
|---|---|
| `670e0d0` | SQLite 書き込み専用スレッドで lock 競合を完全排除 |

症状: 1 セッションで `database is locked` 警告が **202 件** (API_USAGE: 63 件、OCR_LEARN: 139 件)。

原因: 複数スレッド (BG_WORKER + Gemini 8 並列ワーカー + メトリクス記録) がそれぞれ独立した sqlite3.Connection で同時書き込み試行。busy_timeout 5 秒では捌けず失敗。

設計 (案 B 採用): 書き込み専用スレッド `WriteWorker` を 1 つ立ち上げ、queue.Queue で受け取った SQL を順次実行。複数の呼び出し元から submit されても worker 内で直列化されるため lock 競合は発生しない。

実装:
- `crawler/tools/ap/write_worker.py` (189 行): WriteWorker クラス + singleton + drain shutdown
- `crawler/tests/test_write_worker.py` (10 件、 50 スレッド × 10 件 = 500 件直列化検証含む)
- `api_usage.py`: `conn=None` の主経路を WriteWorker.submit (async)
- `ocr_correction.py`: 全書き込みを WriteWorker.submit
- `auto_pilot.py`: シャットダウン時に drain + close

検証: 修正後 `database is locked` 警告 **0 件** (再起動後継続)。

| OCR テキスト | 種類 | あるべき動作 |

| `"ストーリーをスキップする。"` | ストーリースキップ | キャンセル (現状) |
| `"ムービーをスキップしますか？"` | ムービースキップ | **OK タップ** ← 新規対応 |
